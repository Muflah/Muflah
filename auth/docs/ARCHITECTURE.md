# Authentication Architecture

## Service boundary

The auth service is a self-hosted modular monolith. It runs as its own application, database, deployment, and subdomain. Products integrate through standard HTTP and JSON APIs.

Current deployment target:

```text
https://auth.muflah.com
```

The design keeps Better Auth as an external runtime dependency. The repository owns configuration, email delivery, UX, password policy, trusted-device policy, and future product-neutral session behavior.

## Main components

```text
Browser / product client
        │
        ▼
Next.js app and JSON routes
        │
        ├── Better Auth HTTP handler
        ├── email-first auth UI
        ├── signup-flow routes
        └── password reset UI
        │
        ├── Better Auth
        │     ├── email/password credentials
        │     ├── email OTP verification
        │     ├── two-factor OTP
        │     ├── trusted-device cookies
        │     └── multi-session account switching
        │
        ├── Resend email adapter
        └── PostgreSQL database
```

## Authentication layers

### Identity and credentials

Better Auth owns users, credential accounts, sessions, verification records, and the two-factor schema. The auth service also owns the platform-wide identity profile: name, globally unique username, date of birth, and onboarding state. Password hashes are stored in the `account` table under the `credential` provider, not in the `user` table.

### Email verification

The email OTP plugin verifies signup email ownership. Signup verification has a dedicated route so email verification cannot accidentally invoke the login flow or remove an existing credential. Password creation and profile completion are separate steps, allowing an incomplete account to resume onboarding.

### Risk-based login OTP

The two-factor plugin runs after password authentication. It checks the signed trusted-device cookie. Trusted devices proceed directly; untrusted devices receive an email OTP challenge.

### Email delivery

The auth service calls a local email integration interface. The current adapter sends through Resend. The configured domain is provider-neutral; sender aliases are generated by the application.

```text
AUTH_EMAIL_DOMAIN=mail.muflah.com
```

The current default alias is `no-reply@<AUTH_EMAIL_DOMAIN>`.

### Cross-subdomain session cookies

Cross-subdomain cookies are opt-in through `AUTH_COOKIE_DOMAIN`. Setting it to `muflah.com` makes the secure, HTTP-only Better Auth session cookie available to Muflah subdomains. Leaving it empty keeps the cookie host-only. This shares the browser credential but does not automatically integrate a product: each consuming app must use the auth API with credentials and an approved origin policy. A parent-domain cookie also means a compromised sibling subdomain can affect the shared session, so only trusted Muflah subdomains should participate.

### Account sessions

The official Better Auth multi-session plugin keeps multiple account sessions available in one browser. The service configures its maximum from `AUTH_MAX_SESSIONS`, with a safe fallback of one for invalid values. The UI lists available sessions, activates a selected session, and starts the normal root signup flow when the user chooses to add another account. The session table remains Better Auth-owned; the service does not create a parallel session store.

## Database ownership

The auth service owns its PostgreSQL database. Applications should not directly write to auth tables. Database migrations are deliberate deployment steps and are not run automatically by every Vercel build.

## Application authorization

Roles and permissions are intentionally outside this service. Product applications may associate their own memberships and authorization policies with the auth user ID.

## Route boundary

The root route owns authentication. `/onboarding` owns incomplete platform profile setup. The dynamic `/<username>` route is the authenticated landing surface for completed profiles. The username is read from the persisted auth user profile and is never hard-coded as a literal route name.

## Release approach

The service uses rolling releases. Schema and API changes must remain compatible while old and new instances overlap. Public JSON contracts should evolve additively.
